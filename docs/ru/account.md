# Аккаунт WARP

[← Назад к README](../../README_RU.md)

```sh
warpscout register
```

Команда записывает `warpscout-account.json` в текущую директорию. Без этого файла `scan`, `find-junk`, `find-sni` и `socks` не запустятся. `-a/-account FILE` кладёт файл в другое место, и тот же флаг подсказывает остальным командам, где его искать.

## Как происходит регистрация

WARPSCOUT делает то же, что официальный клиент WARP при первом запуске: регистрирует в Cloudflare новое устройство и получает для него пир WireGuard.

1. Локально генерируется свежая пара ключей X25519. Приватная половина остаётся на вашей машине.
2. Публичная половина уходит на `https://api.cloudflareclient.com/v0a4005/reg` под видом Android-клиента. В ответ приходят `id` аккаунта, bearer-токен и публичный ключ пира WARP.
3. Второй запрос включает для этого аккаунта WARP (`warp_enabled: true`).
4. Результат записывается в файл аккаунта.

```json
{
  "id": "...",
  "token": "...",
  "private_key": "...",
  "peer_public_key": "...",
  "ipv4": "172.16.0.2",
  "ipv6": "2606:4700:110:...",
  "masque": { "id": "...", "token": "...", "private_key": "...", "peer_public_key": "..." },
  "outer": { "id": "...", "token": "...", "private_key": "...", "peer_public_key": "..." }
}
```

| Поле              | Что это                                                                                                                            |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `id`              | Аккаунт, созданный Cloudflare. Адресует последующие запросы                                                                        |
| `token`           | Bearer-токен, который эти запросы авторизует. И то, и другое - секреты                                                             |
| `private_key`     | Своя сторона туннеля. Она же попадает в конфиги `-conf`                                                                            |
| `peer_public_key` | Публичный ключ пира WARP - общий для всех эндпоинтов, поэтому одного аккаунта хватает на все                                       |
| `ipv4`            | Адрес внутри туннеля WARP. У всех одинаковый и уходит наружу через NAT                                                             |
| `ipv6`            | Собственный маршрутизируемый v6-адрес. Трафик с чужого отбрасывается                                                               |
| `masque`          | Второе устройство, зарегистрированное как [MASQUE](masque.md) - одно устройство не может быть и тем и другим                        |
| `outer`           | Третье устройство под внешний туннель [WARP-in-WARP](warp-in-warp.md)                                                              |

`masque` и `outer` создаются best-effort: если Cloudflare откажет в каком-то из них, `register` предупредит, а остальной файл продолжит работать.

## Повторный запуск

При повторном запуске `id` и `token` берутся из файла, а меняются только ключи: генерируется новая пара и уходит через `PATCH`, так что новый `private_key` появляется без ещё одной регистрации.

Новый аккаунт создаётся в двух случаях: при `-fresh`, который игнорирует файл целиком, и при неудачной ротации (отозванный токен, удалённый на стороне Cloudflare аккаунт).

## Когда API недоступен

В фильтрующей сети регистрационные запросы наружу не уходят вовсе. WARPSCOUT обходит это по цепочке.

1. **Напрямую.** Проверяется, отвечает ли `api.cloudflareclient.com`.
2. **Через реле.** Небольшой обратный прокси, который DPI обычно не трогает. Адрес по умолчанию зашит, `-relay URL` подставляет свой, `-relay none` пропускает шаг. Как поднять своё реле - в репозитории [nellimonix/base-relay](https://github.com/nellimonix/base-relay).
3. **Через туннель WARP.** Перебираются адреса эндпоинтов, поднимается туннель к первому, с которым прошло рукопожатие, и те же самые регистрационные запросы отправляются уже через него. Сначала пробуется AmneziaWG, затем обычный WireGuard, а для AmneziaWG перебирается ещё и несколько разных первых пакетов (`I1`).

При наличии прокси `-x/-proxy` отправляет регистрацию через него, и запасные пути не задействуются вообще:

```sh
warpscout register -x socks5://127.0.0.1:1080
```
